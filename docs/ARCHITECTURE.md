# Architecture

This document describes the **0.3.0-beta1** architecture and the invariants a future port should preserve.

## Purpose and core design

Custom Spawn Categories adds a new MCreator mod element named **Spawn Category**. Each element extends Minecraft/NeoForge's `MobCategory` enum and can be selected by Living Entities as an independent natural-spawn category.

The plugin relies on Minecraft's normal `NaturalSpawner`; it does **not** own a parallel spawn loop.

## Data flow

```text
Spawn Category mod element
        |
        +-- editable category identifier
        +-- base mob cap
        +-- friendly flag
        +-- periodic 400-tick spawn-check flag
        +-- despawn distance
        +-- placement preset/custom configuration
        +-- optional category spawn-condition procedure
        |
        +--> META-INF/enumextensions.json
        |       extends net.minecraft.world.entity.MobCategory
        |
        +--> <JavaModName>MobCategories.java
        |       constants / resolver / procedure helpers
        |
        +--> Living Entity GUI
        |       displays custom categories
        |       stores CUSTOM:<MCreatorModElementName>
        |
        +--> Living Entity generator override
                resolves custom MobCategory
                registers custom spawn placement predicate
```

## Stable identity versus editable identifier

There are two names with different jobs:

```text
MCreator mod-element name
    stable internal reference used by Living Entities
    stored as CUSTOM:<ModElementName>

Category identifier
    user-editable MobCategory/enum-extension identifier
    shown to users and emitted into generated category data
```

Do not collapse these into one value. The indirection is what lets users rename the Category identifier without breaking existing Living Entity references.

## MCreator-side Java

### `Launcher`

Registers the custom mod-element type during `PreGeneratorsLoadingEvent` and installs the Living Entity GUI bridge.

### `PluginElementTypes`

Registers `spawncategory` through `ModElementTypeLoader.register(...)`.

### `SpawnCategory`

Serialized data model for the custom mod element.

### `SpawnCategoryGUI`

Provides editor controls, validation, procedure selection, duplicate-identifier handling, and regeneration of Living Entities that reference the edited category.

The category-level spawn-condition procedure receives only:

```text
x, y, z, world
```

No entity instance exists yet during the spawn-placement predicate.

### `LivingEntitySpawnCategoryBridge`

Reflectively accesses the private `LivingEntityGUI.mobSpawningType` combo box, appends custom Spawn Category choices, and restores custom selections when reopening a Living Entity.

This reflection contract is a high-risk MCreator compatibility point and is explicitly checked by the compatibility tool.

MCreator 2026.1 versus 2026.2 proved why this matters: the serialized `LivingEntity.mobSpawningType` representation changed from a plain `String` to a `MobSpawnType` wrapper while much of the surrounding API still compiled.

## Generator-side integration

### `spawncategory.definition.yaml`

The known-good shared-helper generation mechanism is:

```yaml
global_templates:
  - template: spawncategory/custom_mob_categories.java.ftl
    name: "@SRCROOT/@BASEPACKAGEPATH/init/@JavaModNameMobCategories.java"
```

This was verified by deleting generated files and regenerating from scratch. During Alpha 19, alternative generation approaches failed to recreate the helper reliably. Do not replace this path merely because another mechanism appears newer.

Per-element `*Definition.java` files are secondary/diagnostic. Their presence alone is not proof they were generated by the current build because stale files can survive regeneration.

### `<JavaModName>MobCategories.java`

Generated workspace helper containing custom category constants/resolution and procedure helper methods. Living Entity generated code depends on it.

A missing helper while Living Entities reference it is a release-blocking generation failure.

### `generator.yaml`

Extends the generator's base enum-extension output so normal NeoForge entries and Spawn Category `MobCategory` entries coexist in one `META-INF/enumextensions.json`.

### `enumextensions.json.ftl`

Adds each Spawn Category to:

```text
net/minecraft/world/entity/MobCategory
```

Tested Beta 1 constructor descriptor:

```text
(Ljava/lang/String;IZZI)V
```

Tested semantic presentation:

```text
String name
int max
boolean friendly
boolean periodic 400-tick spawn checks
int despawn distance
```

The fourth parameter must **not** be described as individual entity persistence.

### `neoforge.mods.toml.ftl`

Emits:

```text
enumExtensions="META-INF/enumextensions.json"
```

when required, while preserving upstream NeoForge behavior.

### `mappings/mobspawntypes.yaml`

Keeps vanilla mappings and adds custom-entry resolution through `<JavaModName>MobCategories.resolve(...)`.

### Living Entity whole-file override

```text
src/main/resources/<generator-id>/templates/livingentity/livingentity.java.ftl
```

is the largest long-term maintenance risk because it overrides the **entire upstream template**.

On every generator update:

1. obtain the new upstream template;
2. diff old-upstream versus new-upstream;
3. begin with the new-upstream file;
4. reapply only the plugin's custom-category changes;
5. review generated Java;
6. run destructive regeneration/runtime tests.

Never copy the old plugin override into a new generator folder unchanged and call the port complete.

## Spawn placement precedence

For a Living Entity assigned to a custom Spawn Category:

1. Living Entity's own spawning-condition procedure, if present;
2. Spawn Category's category-level spawn-condition procedure, if present;
3. Spawn Category's configured placement condition.

This preserves entity-specific overrides while allowing category-wide defaults.

## Procedure blocks

Beta 1 includes:

```text
Entity [entity] belongs to spawn category [category]
Number of loaded entities in spawn category [category]
```

Selectors combine MCreator's vanilla `mobspawntypes` data list with `spawncategory` custom entries.

The loaded-count helper caches counts once per `ServerLevel` game tick. It counts loaded, non-removed entities by `EntityType#getCategory()`. It is a useful diagnostic/population tool but is **not** specified as Minecraft's exact internal natural-spawn census.

## Mob-cap and persistence behavior

MCreator Living Entities with **Despawn when idle disabled** call `setPersistenceRequired()`. Persistence-required mobs are not a reliable population for Minecraft's natural spawn cap to constrain as a hard loaded-entity ceiling.

Therefore:

```text
custom cap looks broken + Despawn when idle disabled
```

is not sufficient evidence of a Spawn Category bug. Re-test with **Despawn when idle enabled**.

This behavior is completely separate from the Spawn Category flag **Use periodic 400-tick spawn checks**.

## Canonical source versus generated evidence

### Canonical source

```text
src/main/java/**
src/main/resources/**
compatibility-spec.json
```

### Generated workspace evidence

```text
<JavaModName>MobCategories.java
*Definition.java
META-INF/enumextensions.json
Living Entity generated Java
```

Generated files are essential for verification, but permanent fixes belong in the plugin source/templates, not in a workspace's generated output.

## Highest-risk compatibility points

Inspect these first on a port:

- `LivingEntityGUI.mobSpawningType` reflection target.
- serialized `LivingEntity.mobSpawningType` data type/representation.
- `ModElementGUI`, `ProcedureSelector`, and reload APIs used by the editor.
- `global_templates` generation semantics.
- `mobspawntypes` data-list/mapping format.
- upstream `livingentity.java.ftl` spawn-placement code.
- `MobCategory` enum-extension constructor descriptor.
- NeoForge enum-extension JSON/TOML registration.
- `RegisterSpawnPlacementsEvent` API.
- `EntityType#getCategory()` behavior.
- server-level entity iteration used by the count helper.
